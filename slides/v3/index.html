01 The problem

Security tools should be easier to run.

Many developers do not scan often because setup is slow, reports are noisy, and each language needs different tools.

HermSec turns that work into one simple desktop flow.

Inspect and choose Detects languages, frameworks, and manifests. Selects adaptive scanners like Semgrep, Gitleaks, OSV, Trivy, and Bandit only when useful.
Scan and normalize Runs managed scanners safely, then turns every result into one HermSec finding format with evidence and fingerprints.
Report and explain Writes JSON, HTML, Markdown, dashboard, and PDF output with clear evidence and remediation guidance.

02 How the harness works

Deep assisted scan is scanner-backed review plus model explanation.

HermSec checks what the project is, prepares the right tools, runs scanners, normalizes evidence, and asks the model to explain confirmed findings.

InspectFind languages, frameworks, manifests, lockfiles, and config files.
Choose toolsPick Semgrep, Gitleaks, OSV, Trivy, Bandit, and others only when useful.
Run scansExecute managed scanners safely, with timeouts and progress events.
NormalizeTurn every result into one HermSec finding format with evidence and fingerprints.
ReportWrite JSON, HTML, Markdown, dashboard artifacts, and PDF output.

03 Review modes

We compared four ways to review code.

Each mode uses the same report format, but the evidence is collected and judged differently.

Deep assistedScanners run first. The model summarizes and explains scanner-backed evidence.
Single AgentOne model inspects focused code candidates with bounded read and search tools.
MoASpecialist agents inspect candidates. A judge and aggregator merge accepted evidence.
Scanner + MoAScanners and agents run independently. A judge validates and merges both evidence sources.
Scanner-backedinspect -> choose scanners -> run scanners -> model explanation -> report
Agent-onlycandidate discovery -> focused task bundle -> one agent -> local evidence check
Multi-agentcandidate discovery -> specialist agents -> false-positive judge -> aggregator
Hybridscanner findings + independent MoA candidates -> judge -> final revalidation

07 Scanners vs agents

How scanners and agents complement each other.

08 Language coverage gaps

F1 score grouped by language family.

JavaScript / TypeScript (avg 0.87) Best coverage. Node.js and Express apps have mature scanner rules and heuristic patterns.
Go (0.86) Strong results. Go scanner rules are effective for web application patterns.
Java (0.79) Good results but servlet-specific patterns like deserialization need better rules.
Python (0.74) Moderate. Bandit covers basics but framework-specific issues are missed.
PHP / Ruby / C# (avg 0.73) Similar performance. Scanner rules exist but MoA agents add limited value.
Rust (0.60) and C/C++ (0.55) Lowest scores. Limited heuristic rules and scanner coverage for memory safety patterns.

09 Future plans & limitations

What comes next.

Next we make HermSec smaller, faster, and more automatic.

Better language coverageImprove C/C++ and Rust language coverage in the heuristic scanner and MoA agents.
Public benchmarksTest HermSec on OWASP Benchmark, OpenSSF CVE Benchmark, and CASTLE test suites.
Rate limit handlingAdd retry logic and rate limit handling for model providers during sequential scans.
Cost trackingMeasure model token cost per mode and route work to efficient models by default.

Threats to validity

Synthetic vulnerabilities may not reflect real-world code complexity
CWE-based scoring may miss useful findings not in the ground truth
Model behavior can change due to provider errors and updates
Small dataset size limits generalizability of results
