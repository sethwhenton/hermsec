Hermsec desktop architecture

How the Hermsec UI and desktop app were built

Hermsec is a local-first security assistant. The desktop app gives the user a chat UI, settings screens, project history, scanner management, and report dashboards. Behind the UI, it calls the root Hermsec CLI and scan harness to inspect a local repository.

Desktop shell Electron creates the app window and controls local files, dialogs, reports, and child processes.
Web UI React renders the sidebar, chat, dashboards, settings, models, providers, and scanners.
Scan engine The root CLI runs the scan harness, scanner tools, model support, and report renderer.

2. The Three Desktop Layers

Electron apps usually split work into main, preload, and renderer code.

Main process

desktop/src/main/index.ts creates the BrowserWindow, loads the renderer, sets safe browser behavior, loads environment files, and registers IPC handlers. It also calls configureBundledRuntime() so packaged scanner tools are on the path.

Preload bridge

desktop/src/preload/index.ts exposes a typed window.hermsec API with contextBridge. This is the safe door between the web UI and the main process.

Renderer app

desktop/src/renderer/src/App.tsx renders AppShell. The renderer is the React side that the user sees: chat, sidebar, settings, dashboard, and automation screens.

Simple explanation for class The renderer is like the front desk. The preload script is the security window. The main process is the staff room where the app can safely touch the computer.

4. Project, Sidebar, and Chat Flow

This is the normal path when a student clicks around the app.

The sidebar loads projects and sessions. LeftSidebar.tsx calls api.projects.list() and refreshSessions(). Projects come from projects.json. Chat summaries come from sessions.json.
The user chooses a project or starts a new chat. The selected project path becomes settings.defaultProjectDir. settingsStore.ts also registers that project in the main process.
The chat decides what the user means. ChatView.tsx classifies text as a scan, automation setup, Doctor check, fix prompt, capability question, or normal report conversation.
The report store runs scan actions. reportStore.ts calls api.scan.project(), subscribes to api.scan.onProgress(), and stores the latest report paths for the dashboard.
The session store saves the conversation. sessionStore.ts creates or updates a chat session after messages, questions, and scan progress are added.

5. Settings, Providers, Models, and Scanners

Hermsec separates user choices from scan execution.

Settings screen

SettingsPanel.tsx switches between GeneralSettings, AgentsSettings, ProvidersSettings, ModelsSettings, and ScannersSettings. The screen is driven by uiStore.ts.

General settings

GeneralSettings.tsx controls language, auto-accept permissions, terminal shell, privacy mode, default scan mode, project directory, report directory, and automation status.

Providers and models

providerCatalog.ts defines provider presets like OpenCode Go, OpenRouter, Ollama, OpenAI, Anthropic, Google Gemini, and Cursor. providerTest.ts tests the provider by calling model list endpoints such as /models.

Scanner management

ScannersSettings.tsx shows installed and missing scanner tools. desktop/src/main/scanners.ts can install supported tools into a Hermsec-managed folder, and it passes scanner choices to the CLI through environment variables.

6. How a Scan Runs

The desktop does not contain all scanning logic. It calls the root CLI.

The renderer asks for a scan. ChatView.tsx calls useReportStore().runScan() with a target path, report directory, scan mode, and assist mode.
The main process receives scan:project. ipc.ts forwards the request to desktop/src/main/scan.ts. Progress updates are sent back as scan:progress.
The desktop finds and starts the CLI. scan.ts builds a command like node dist/src/bin/hermsec.js scan TARGET --mode online --assist-mode deep-assisted --out REPORT_DIR --json --html.
The CLI calls the harness. src/cli/commands/scan.ts parses flags, then src/core/harness.ts calls src/core/scan.ts. The scan can run repository discovery, built-in heuristics, external scanners, model explanation, agent modes, and vulnerability intelligence.
Reports are written back to disk. src/reports/reportRenderer.ts writes files like report.html, summary.json, findings.json, evidence.json, run.json, agent-summary.json, delta.json, and report-document.json.
The desktop builds presentation artifacts. desktop/src/main/reportArtifacts.ts creates dashboard/index.html, onepager/index.html, and, when possible, onepager/report.pdf with Electron's printToPDF().

7. Local Data and Storage

Hermsec stores app state locally instead of depending on a cloud database.

Data Where it is handled What it means
Desktop settings desktop/src/main/store.ts Stored as settings.json in Electron userData. Includes scan mode, providers, models, agents, scanner settings, project path, report path, and automation settings.
Project list desktop/src/main/projects.ts Stored as projects.json. Archive and delete only hide projects inside Hermsec; they do not delete the real project folder.
Chat sessions desktop/src/main/sessions.ts Stored as sessions.json. Each session has project path, title, timestamps, message count, and chat items.
Report output settings.defaultReportDir and src/reports/reportRenderer.ts Default location is under the user's Documents folder: Hermsec/reports. Each scan gets its own report directory.
Managed scanner tools desktop/src/main/scanners.ts Installed under userData/managed-scanners/<platform>-<arch>, not inside the scanned repository.
Root CLI app data src/storage/platformPaths.ts Uses HERMSEC_HOME when set. Otherwise it uses platform paths such as %APPDATA%/Hermsec on Windows.

8. IPC Architecture

IPC means inter-process communication. It is how the web UI talks to Electron's main process.

What the preload exposes

desktop/src/preload/index.ts exposes groups named settings, provider, doctor, scanners, projects, sessions, reports, scan, and window.

What the main process handles

desktop/src/main/ipc.ts registers handlers such as settings:get, provider:test, scanners:list, projects:add, sessions:create, reports:converse, and scan:project.

Why this matters The renderer runs like a web page, so it should not directly use Node file APIs or child processes. The preload bridge keeps that boundary clear.

9. Packaged App and Runtime Tools

Packaging prepares Hermsec so users can scan without manually setting up every tool.

Build and packaging scripts

desktop/package.json defines build:packaged, dist:win, dist:mac, and dist:linux. The packaged app includes the built renderer, main process, preload script, resources, and icons.

Bundled root CLI

desktop/scripts/prepare-cli-bundle.mjs builds the root TypeScript CLI and copies dist/src into desktop/resources/hermsec-cli. runtimeBundle.ts can then find that CLI inside packaged resources.

Bundled scanner tools

desktop/scripts/prepare-runtime-tools.mjs prepares tools under desktop/resources/runtime-tools/<platform>-<arch>. The script covers native tools such as Gitleaks, OSV-Scanner, and PMG, plus Python tools such as Semgrep, Bandit, and pip-audit.

Runtime setup

desktop/src/main/runtimeBundle.ts adds bundled tool folders to PATH, sets scanner override environment variables like HERMSEC_SEMGREP_BIN, disables scanner telemetry where possible, and points packaged scans at the bundled CLI.
