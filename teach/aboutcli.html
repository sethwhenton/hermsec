HermSec teaching page

How the HermSec CLI and scanning pipeline work

This page explains the code path from a terminal command to final security reports. The language is simple so a first-year university student can present it and answer questions.

One sentence summary

  • HermSec reads a project, chooses safe scanners, normalizes evidence, optionally asks a model to explain or judge results, matches advisories, and writes reports.

1. Big Picture

HermSec has a command line interface, or CLI. A user types a command like hermsec scan ./project. The CLI then starts a pipeline. A pipeline is a set of steps that pass information forward.

1 Read command The CLI parses the target folder, scan mode, assist mode, output folder, and output formats.
2 Inspect project HermSec walks the files, detects languages, finds manifests and lockfiles, and reads Git data.
3 Run evidence tools Built-in heuristics and external scanners look for code, dependency, secret, config, and supply-chain risks.
4 Normalize results Findings get stable fields, safe evidence, relative paths, fingerprints, and duplicate handling.
5 Use model help Depending on the assist mode, the model explains scanner evidence or inspects focused candidates.
6 Match advisories HermSec checks CVE, GHSA, OSV, NVD, and CISA KEV style intelligence against packages and findings.
7 Build reports The report layer writes JSON, Markdown, HTML, dashboard pages, a one-page view, and sometimes PDF.
8 Show progress Progress events mark repository, scanner, model, and report checkpoints during the run.
Speaker note

You can describe HermSec as a "security evidence pipeline." The important idea is that scanners and local scripts create the evidence, while the model is controlled so it does not invent facts.

2. Command Entry Points

The CLI starts in src/bin/hermsec.ts. That file calls runCli from src/cli/index.ts. The command router is in src/cli/program.ts.

The scan command is implemented in src/cli/commands/scan.ts. It accepts the target project and flags such as output format, scan mode, and assist mode. 

hermsec scan <target> \
  --mode auto \
  --assist-mode deep-assisted \
  --out .hermsec/reports \
  --json --md --html
CLI piece What it does
src/bin/hermsec.ts Starts the command line program and handles top-level errors.
src/cli/program.ts Routes commands such as scan, agent, report, doctor, and workspace.
src/cli/args.ts Parses flags and resolves local paths from the current working directory.
src/cli/moduleSpecs.ts Points the scan command to src/core/harness.ts and its runScan export.
src/cli/optionalModule.ts Dynamically imports the scan module, checks the export, and normalizes the returned result.

Scan modes are auto, offline, and online. Assist modes are deep-assisted, single-agent, moa-assisted, and scanner-moa-assisted.

3. Project Inspection

Before scanning, HermSec needs to know what kind of project it is reading. The file walker in src/core/files.ts lists files, detects languages, and marks special files such as package manifests and lockfiles.

The repository summary in src/core/repository.ts adds useful facts: Git branch, commit, dirty state, languages, package managers, manifest files, lockfiles, and ignored folders.

Included examples

HermSec recognizes JavaScript, TypeScript, Python, Java, PHP, Go, Rust, Ruby, C/C++, C#, Kotlin, Swift, Dart, HTML, Vue, Svelte, Terraform, JSON, XML, YAML, TOML, Gradle files, and more.

Ignored examples

It skips noisy or generated folders such as .git, node_modules, vendor, dist, build, coverage, .next, .cache, and __pycache__.

This inspection matters because HermSec should not run every scanner on every project. For example, a Python scanner should run only when Python files or Python package files are present.

4. Scanner Registry, Selection, and Installation

HermSec has a scanner catalog in src/scanners/catalog.ts. The catalog describes each scanner: its name, command, category, supported languages, input files, install type, and risk notes.

  • hermsec-heuristics
  • semgrep
  • gitleaks
  • trufflehog
  • osv-scanner
  • trivy
  • checkov
  • bandit
  • pip-audit
  • retire
  • findsecbugs
  • dependency-check
  • gosec
  • govulncheck
  • cargo-audit
  • brakeman

External scanner execution is handled by src/scanners/external.ts. It checks whether a scanner is enabled, whether the project has matching files, and whether the scanner executable is available.

The desktop app adds installation support in desktop/src/main/scanners.ts. It can auto-install supported scanner tools into HermSec managed storage using safe install plans. It then passes scanner paths and settings to the CLI through environment variables.

Safety point

HermSec does not let scanners run arbitrary shell commands. src/scanners/process.ts uses spawn with shell:false, timeouts, output caps, allowed executable names, and blocked dangerous arguments such as install, update, build, run, test, exec, publish, fix, and apply.

5. Heuristics and Java Taint

HermSec always has one built-in scanner: hermsec-heuristics. It lives in src/scanners/heuristics.ts. A heuristic is a rule-based check. It is not a full compiler or a full security proof, but it can quickly find common risky patterns.

Common heuristic checks

  • Secrets, such as private keys and hardcoded tokens, with redacted evidence.
  • JavaScript and TypeScript risks, such as eval, unsafe process execution, wildcard CORS, and unsafe HTML writes.
  • Python risks, such as shell=True, os.system, unsafe YAML loading, and disabled TLS verification.
  • Package and supply-chain risks, such as risky dependency ranges, install scripts, missing lockfiles, and known vulnerable versions.
  • Config risks, such as committed environment files, risky GitHub Actions, privileged containers, and shell pipes in Dockerfiles.

Java taint in simple terms

The Java logic tracks whether user-controlled data moves from a source to a dangerous sink. A source is input such as request.getParameter, request headers, cookies, body readers, session values, or uploaded file names.

A sink is an operation that could be dangerous, such as SQL execution, command execution, LDAP search, XPath evaluation, file path access, redirects, response writes, weak crypto, weak hashes, weak randomness, or insecure cookies.

The Java taint logic also checks sanitizer families. For example, HTML encoding helps with HTML output, SQL encoding helps with SQL contexts, and URL encoding helps with URL contexts. HermSec tries to match the sanitizer to the sink type instead of treating all sanitizers as equal.

6. Agent Modes and Model Help

The high-level scan harness is src/core/harness.ts. It decides whether to run scanners, whether to call model assistance, whether to run advisory intelligence, and when to render the report.

Assist mode Scanner use Model or agent role
deep-assisted Runs built-in and external scanners. The model explains, prioritizes, and connects scanner-backed findings. It must use only scanner evidence.
single-agent Does not run scanner tools. One agent inspects bounded project context. Local focused candidates are still generated first and kept if useful.
moa-assisted Does not run scanner tools. Several specialist agents inspect the project, then a false-positive judge and an aggregator merge the useful findings.
scanner-moa-assisted Runs scanner tools and MoA independently. Scanner findings and agent candidates are judged, deduplicated, and merged together.

Candidate-first agent mode

Product agent modes use a candidate-first design in src/agent/productScan.ts and src/agent/focusedCandidates.ts. A candidate is a possible finding with file, line, evidence, and reason. HermSec prefers to start with concrete candidates, then ask the model to review, judge, and merge them.

The code inspection runtime in src/agent/codeInspection.ts gives the model bounded, read-only tools such as listing files, searching code, and reading short snippets. It keeps the agent inside the repository and redacts secret-like text from snippets.

7. Prompts, Instructions, and Responsibilities

HermSec separates script responsibilities from model responsibilities. This is important because security reports need evidence, not guesses.

Scripts do
Walk files, detect languages, run scanners, parse outputs, normalize findings, redact evidence, deduplicate results, build package inventory, match advisories, and write report files.
Models do
Explain scanner findings, rank risk, inspect bounded code snippets, judge candidates, and aggregate accepted candidates into readable findings.
Models must not do
Invent files, line numbers, packages, versions, scanners, CVEs, GHSA IDs, OSV IDs, or CWEs. They also must not ask to install packages, run build scripts, use the network, or provide exploit steps.

The shared model behavior is shaped by src/agent/systemPrompt.ts. Structured model output is checked by src/agent/structuredOutput.ts. If the model output invents unsupported evidence, HermSec can reject it and fall back to safer explanations.

8. Progress Events and Checkpoints

Progress events are created with helpers in src/core/progress.ts. The root stages are repository, scanner, model, and report. Each event has a status such as waiting, running, completed, skipped, or failed.

When the CLI is run with --json, progress is written to stderr as lines that begin with HERMSEC_PROGRESS. The final JSON result stays on stdout, so programs can read the result without mixing it with progress messages.

The desktop scan controller in desktop/src/main/scan.ts maps these events into user-facing checkpoints: inspect-project, choose-tools, prepare-tools, running-scans, model-summary, report-ready, and report-pdf.

9. Normalization and Evidence Safety

Different scanners use different JSON shapes. HermSec turns them into one common finding shape. This is called normalization, and it is handled mainly in src/scanners/normalization.ts and src/scanners/parsers.ts.

  • Every finding gets a title, category, severity, confidence, tool name, evidence, and remediation text.
  • File paths are made relative to the scanned project when possible.
  • Evidence is clamped and redacted so secrets are not printed into reports.
  • Stable fingerprints help HermSec identify duplicates and compare reports over time.
  • Identifiers such as CVE-..., GHSA-..., OSV-..., PYSEC-..., RUSTSEC-..., and GO-... are extracted when scanners provide them.

This common shape makes later steps easier. The report layer, model layer, and advisory matcher can all read the same kind of finding object.

10. CVE, Advisory, and KEV Matching

Vulnerability intelligence is added after scanning in non-agent-only modes. The main entry point is src/intel/reportEnrichment.ts. It builds a package inventory from findings, manifests, and lockfiles.

The matcher in src/intel/matcher.ts compares package names, ecosystems, versions, finding identifiers, and CWE hints to advisory data. It gives higher priority when there is strong evidence, such as an exact advisory identifier or a package version inside an affected range.

HermSec can use sources defined around src/intel/sourceRegistry.ts and src/intel/updater.ts, including CISA Known Exploited Vulnerabilities, OSV, GitHub Advisory data, and NVD. CISA KEV matters because it marks vulnerabilities that are known to be exploited in the real world.

Offline behavior

The intelligence layer uses cached data when possible. If online updates are not available, it can fall back to local cached or vendor data instead of stopping the whole scan.

11. Report Generation: JSON, HTML, Markdown, and PDF

Reports are built in src/reports/reportRenderer.ts. The report renderer validates the report document, writes an evidence bundle, compares with a previous report when available, and writes the requested formats.

Output Where it comes from Purpose
summary.json, findings.json, evidence.json, run.json src/reports/jsonRenderer.ts Machine-readable scan results and evidence.
report.md src/reports/markdownRenderer.ts A readable text report for developers and review systems.
report.html and report.css src/reports/htmlRenderer.ts A standalone browser report with summary, findings, scanner status, intelligence, evidence, and limitations.
dashboard/index.html and onepager/index.html desktop/src/main/reportArtifacts.ts Desktop-friendly report views built from the same report document.
onepager/report.pdf desktop/src/main/reportArtifacts.ts A PDF export made by Electron when the desktop app can print the one-page view.

The report also states limitations. For example, model explanations cannot add new CVEs, file paths, package versions, or line numbers that were not supplied by scanner or code evidence.

12. Practice Answers for Class Questions

Why does HermSec inspect the project first?

It needs to know what languages and package files exist. This helps it choose scanners that make sense and avoid wasting time on tools that cannot help.

What is the difference between deep-assisted and Scanner + MoA?

Deep-assisted starts with scanner findings and asks the model to explain and prioritize them. Scanner + MoA runs scanners and model agents more independently, then judges and merges both evidence sources.

Can the model invent a CVE?

No. The prompts and validators tell the model to use only supplied evidence. If a CVE, GHSA, OSV ID, file, package, or line number is not in the evidence, the model should not add it.

Why are external scanners run carefully?

Scanners are programs. HermSec limits how they run by using safe command plans, no shell execution, timeouts, output caps, and blocked dangerous arguments.

What is Java taint tracking?

It is a simple data-flow check. HermSec watches user input move through variables. If that input reaches a dangerous operation without the right kind of sanitizer, HermSec reports a possible issue.
